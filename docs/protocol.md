# Pi ↔ Android Protocol

Implemented by `companion/comms/protocol.py` (Pi) and
`android/app/.../comms/Protocol.kt` (Android) - keep both in sync when this
changes. Two separate channels, per docs plan M5/M6:

- **Control/telemetry**: WebSocket, JSON, Pi runs as the server. Every
  message is wrapped in an envelope: `{"type": str, "seq": int, "ts": float, "payload": {...}}`.
- **Video**: WebRTC, signaled over the same control channel via the
  `webrtc_offer` / `webrtc_answer` message types below, but the media itself
  is a separate peer connection - a video hiccup never blocks an abort.
  Deliberately configured with **no STUN/TURN servers on either end**
  (`AiortcVideoPipeline.handle_offer` constructs its `RTCPeerConnection`
  with the aiortc default `RTCConfiguration()`, whose `iceServers` is
  `None`; `WebRtcClient.startReceiving` passes `PeerConnection.
  RTCConfiguration(emptyList())`) - both peers are always on the same LAN
  (the Pi runs its own WiFi AP, see `companion/config/network.yaml`'s
  `mode: ap`), so host ICE candidates alone are sufficient and no external
  server is ever contacted. This is also why the whole system runs with
  **no internet access required at all** once set up: on-sensor AI
  detection (IMX500), the WebSocket control channel, MAVLink, and video are
  all local-network-only, and the Android app has no analytics/cloud SDKs.
  Internet is only needed for one-time setup (`pip install`, `git clone`,
  flashing the Pi OS/IMX500 firmware, the first Gradle build).

## Message types (`payload` shape for each)

| type | direction | payload |
|---|---|---|
| `target_select` | Android → Pi | Drag: `{x, y, w, h}` - bbox in the video's native pixel resolution, matched by IoU against current detections. Tap: `{x, y, point: true}` - matched by point-containment (whichever detection box contains the point, smallest wins on overlap) - see `select_target`/`select_target_at_point` in `companion/tracking/target_selector.py` |
| `mode_command` | Android → Pi | `{mode: "idle"\|"tracking"\|"follow"\|"orbit"\|"approach"\|"grid_search", follow_separation_m?: float, follow_altitude_m?: float, orbit_radius_m?: float, orbit_altitude_m?: float, follow_max_speed_mps?: float, orbit_max_speed_mps?: float, grid_search_width_m?: float, grid_search_height_m?: float, grid_search_heading_deg?: float, auto_takeoff?: bool}` - all optional, and when present immediately override the running `FollowController`/`OrbitController`'s limits (not just at startup from `follow_limits.yaml`/`orbit_limits.yaml`). `follow_altitude_m`/`orbit_altitude_m` switch vertical control from pixel-framing to absolute altitude-hold (via `MavlinkBridge.telemetry.alt_m`). `orbit` is the DJI "circle"/point-of-interest equivalent - see `companion/guidance/orbit.py`. `follow_max_speed_mps`/`orbit_max_speed_mps` (the Android speed slider) go through `FollowController.set_max_speed()`/`OrbitController.set_max_speed()`, which clamp to `[min_speed_mps, the configured max_speed_mps ceiling]` from `follow_limits.yaml`/`orbit_limits.yaml` - the app can only ever dial speed *down* from the safety-vetted config ceiling for extra caution, never up past it from a phone mid-flight; raising the actual ceiling requires editing config, deliberately not exposed as an in-flight control. `grid_search` (a recon/surveillance-relevant "search/grid coverage mode" field request) flies a systematic lawnmower area sweep - see `companion/guidance/grid_search.py`; `grid_search_width_m`/`grid_search_height_m` are required to actually start it (missing either, or no GPS fix, falls back to `idle` rather than silently doing nothing while claiming the mode is active), `grid_search_heading_deg` is optional (default: the aircraft's current compass heading) and orients the swept rectangle. The area is planned from wherever the aircraft currently is at the moment this message is handled - fly to one corner of the area to search, then send this, rather than an interactive map-drawing UI. `auto_takeoff` (a field request: "Arm & Follow should gain height, then start following" - only ever sent `true` by the Android "Arm & Follow" quick action, and only meaningful for a mode that requires GUIDED) hands the mode over to `AutoTakeoffController` (`companion/guidance/auto_takeoff.py`) instead of letting the requested guidance controller start computing setpoints immediately: it sends one `MAV_CMD_NAV_TAKEOFF` once armed and in GUIDED, then withholds all velocity setpoints (`guidance_sent` stays `false` on `tracking_update` even though `supervisor_state` already reports the requested mode) until `telemetry.alt_m` reaches `auto_takeoff_limits.yaml`'s `altitude_m` within `altitude_tolerance_m`, or `timeout_s` elapses and the mode falls back to `idle` |
| `abort` | Android → Pi | `{reason: str}` |
| `arm_command` | Android → Pi | `{armed: bool, force?: bool}` - administrative FC command sent straight to `MavlinkBridge.arm()` (MAV_CMD_COMPONENT_ARM_DISARM), like a standard GCS - independent of the Safety Supervisor's guidance gate, which only concerns itself with velocity setpoints during active AI guidance. `force` is only ever meaningful (and only ever applied) for a disarm, never an arm - ArduCopter refuses an unforced disarm outright if its own land-detector believes the aircraft is flying (real, documented `MAV_CMD_COMPONENT_ARM_DISARM` param2 behavior), which a bench test with props spinning can trip as a false positive; `force: true` sends the command's own documented param2=21196 "force" value to override that refusal. A stray `force: true` alongside `armed: true` is a no-op - arming never bypasses pre-arm checks, by design |
| `arm_command_result` | Pi → Android | `{armed_requested: bool, accepted: bool}` - sent once per real `COMMAND_ACK` the FC returns for the most recent `MAV_CMD_COMPONENT_ARM_DISARM` request (`MavlinkBridge`'s `pending_arm_ack` mailbox, relayed by `CompanionOrchestrator.process_frame`), not repeated. A real, previously-documented gap this closes: this bridge never listened for `COMMAND_ACK` at all, so a pre-arm-check rejection (or ArduCopter's documented refusal to disarm while its land-detector believes the aircraft is flying) was completely invisible - the operator just saw nothing happen. `accepted: false` fires `AlertEvent.ARM_REJECTED`/`DISARM_REJECTED` (picked by `armed_requested`) on the Android side; `accepted: true` fires no alert, since `telemetry.armed` changing is already visible feedback for success |
| `set_flight_mode` | Android → Pi | `{mode: str}` - an ArduCopter mode name (e.g. `"LOITER"`, `"RTL"`); unknown names are a safe no-op (`MavlinkBridge.set_mode` returns `False`, nothing is sent) |
| `record_command` | Android → Pi | `{recording: bool}` - starts/stops the on-Pi local `VideoRecorder` (separate from the WebRTC feed, so footage is preserved even if the wireless link degrades) |
| `recording_state` | Pi → Android | `{recording: bool, duration_s: float}` - sent immediately after a `record_command` is handled, and then again every processed frame for as long as recording stays active so the Android timer keeps ticking (previously only sent once, at toggle time, so the on-screen duration was frozen at whatever it was at that instant even though the recording itself was genuinely running - see `CompanionOrchestrator.process_frame`). The `recording` boolean alone is also mirrored in every `health` message so a reconnecting Android client learns the current state without waiting for a toggle |
| `webrtc_offer` | Android → Pi | `{sdp: str, sdp_type: "offer"}` |
| `webrtc_answer` | Pi → Android | `{sdp: str, sdp_type: "answer"}` |
| `land_confirmation_request` | Pi → Android | `{distance_to_home_m: float\|null, battery_remaining_pct: int\|null, obstacle_detected: bool, obstacle_class_name: str\|null}` - sent once (not repeated) when target-loss recovery's search times out and battery/distance say landing in place is safer than RTL (`companion/guidance/target_recovery.py`). `obstacle_detected`/`obstacle_class_name` come from the same obstacle-proximity check used elsewhere (`companion/safety/proximity_guard.py`) as an informational safety check only, not an automatic veto - the operator makes the actual land/don't-land decision, see `docs/safety-case.md` |
| `land_confirmation_response` | Android → Pi | `{approved: bool}` - the operator's answer. `true` sends `MAV_CMD` via `MavlinkBridge.set_mode("LAND")`; `false` leaves the aircraft as-is (whatever the FC is already doing, e.g. holding under GUIDED's own setpoint-timeout behavior) - landing is never triggered automatically, only on this explicit response |
| `tracking_update` | Pi → Android | `{state, target_id, confidence, bbox: {x,y,w,h}\|null, image_width, image_height, distance_m, supervisor_state, guidance_allowed, guidance_reason, commanded_vx_mps, commanded_vy_mps, commanded_vz_mps, commanded_yaw_rate_rads, guidance_sent}` - the one actively-tracked target, if any. `guidance_reason` is `null` when guidance is running normally, otherwise one of: `stale_subsystems:<names>`, `rc_override`, `obstacle_too_close:<class_name>:<distance>m`, `comms_lost`, `fc_not_in_ai_mode`, `target_lost` (see `companion/safety/supervisor.py`) - the Android app renders this via `GuidanceWarningBanner`. The `commanded_*` fields are the guidance controller's computed velocity setpoint for this frame (`null` when no guidance controller is active), and `guidance_sent` is whether it actually reached `MavlinkBridge.send_velocity_setpoint()` this frame (`false` if a controller computed a command but the Safety Supervisor blocked it, or if `auto_takeoff` is still climbing and withheld the command before a controller ever computed one - see `mode_command`'s `auto_takeoff` field above) - meant to be watched live during a props-off bench test, per the plan's own staged real-flight procedure (M14), not just reviewed after the fact from the session log |
| `detections_update` | Pi → Android | `{image_width, image_height, detections: [{bbox: {x,y,w,h}, class_name, score}, ...]}` - every object currently detected on-sensor, independent of selection/tracking, so the operator can see (and tap) anything the AI recognizes before picking a target |
| `grid_search_update` | Pi → Android | `{active: bool, phase: "IDLE"\|"SEARCHING"\|"FINISHED", waypoints: [[lat, lon], ...], current_index: int}` - sent every frame regardless of mode (mirroring `detections_update`/`tracking_update`), so the app's live map always has current state without needing a separate one-shot "final" message. `waypoints` is the full planned lawnmower route laid out once at `grid_search` mode-command time (`companion/guidance/grid_search.py`'s `generate_lawnmower_waypoints`), `current_index` is which leg endpoint is currently being flown toward |
| `telemetry` | Pi → Android | `{fc_mode, armed, lat, lon, alt_m, groundspeed_mps, battery_voltage_v, battery_remaining_pct, current_battery_a, fence_enabled, fence_breached, satellites_visible, gps_fix_type, hdop, vdop, home_lat, home_lon, distance_to_home_m, home_bearing_deg, roll_deg, pitch_deg, yaw_deg, heading_deg, airspeed_mps, climb_mps, throttle_pct, rc_rssi_pct}` (mirrors `MavlinkBridge.telemetry`) - `fence_enabled`/`fence_breached` come from the FC's real `SYS_STATUS` geofence bit, so the operator can see geofence status live rather than only learning about it if an Approach-Test abort happens to reference it in `guidance_reason`. `satellites_visible`/`gps_fix_type` come from a real `GPS_RAW_INT` message (`satellites_visible` is `null` when the FC reports the standard "unknown" sentinel of 255, not zero satellites) - a real bug found from a UI review: the Android HUD previously showed a hardcoded fake `"12"` for satellite count since nothing populated a real value; `gps_fix_type` follows the standard `MAV_GPS_FIX_TYPE` enum (0/1 = no fix, 2 = 2D, 3+ = 3D or better) and is the authoritative signal for the GPS "FIX"/"NO FIX" indicator, which previously only inferred fix status from `lat` being non-null - a much less precise proxy, since a stale/degraded fix can still report a non-null last-known position. `hdop`/`vdop` are `GPS_RAW_INT.eph`/`epv` (`null` on the standard 65535 "unknown" sentinel). `distance_to_home_m`/`home_bearing_deg` are computed from a real `HOME_POSITION` fix + the current GPS fix via `companion/guidance/geo.py`'s haversine/bearing formulas (both `null` until home is known - see `MavlinkBridge.request_home_position()`); `home_bearing_deg` is the compass bearing from the aircraft's current position toward home (0=true north), used for the Status tab's home-radar widget together with `heading_deg`. `roll_deg`/`pitch_deg`/`yaw_deg` come from a real `ATTITUDE` message; `heading_deg`/`airspeed_mps`/`climb_mps`/`throttle_pct` come from a real `VFR_HUD` message. `rc_rssi_pct` is `RC_CHANNELS.rssi` rescaled from its native 0-254 range to 0-100% (`null` on the standard 255 "unknown" sentinel). `current_battery_a` is `BATTERY_STATUS.current_battery` (centiamps, `null` on the standard -1 "not measured" sentinel) |
| `health` | Pi → Android | `{pi_ok, camera_ok, ai_ok, tracker_ok, mavlink_ok, video_ok, recording, fps, latency_ms, temperature_c}` - `fps` is a real rolling average over the last 30 processed frames; `latency_ms`/`temperature_c` remain placeholders (`null`) until real pipeline timing and Pi thermal-sensor access exist (M12/hardware bring-up) |
| `ping` | Android → Pi | `{...}` - arbitrary payload, echoed back verbatim in the matching `pong`. Answered directly inside `GroundStationLink._dispatch` (`companion/comms/ws_server.py`), bypassing every app-level handler, so a measured round trip reflects the WS transport's own latency floor, not anything guidance-related. Used by `tools/ws_latency_benchmark.py` to measure docs plan M5's "WS control round-trip < 50ms" metric; not otherwise sent by the production Android app today |
| `pong` | Pi → Android | Same payload as the `ping` that triggered it |

All Pi → Android messages are sent every processed frame from
`CompanionOrchestrator.process_frame` (`companion/main.py`), piggybacking on
the camera's frame rate. Sending telemetry/health/detections at full frame
rate is wasteful bandwidth-wise for a real deployment - throttling these to
a lower fixed rate is a natural M12 (performance optimization) follow-up,
not done yet since correctness came first per the plan's priority order.
